# 08.7 — Retain solve completion before observation failure

Type: implementation

Status: resolved (2026-08-05)

Blocked by:

- [Let one Sonnet baseline tell one truth](08.5-let-one-sonnet-baseline-tell-one-truth.md)

Related but scientifically independent:

## Outcome

Persist the existing `ProjectExecution` immediately after a Native solve
completes and before product observation begins. If observation later faults,
the current call and its unchanged exception prove that observation failed;
the retained execution mapping proves only that the solve completed.

This ticket adds no new record type, failure sidecar, exception classifier,
observation, evidence, Authority receipt, `WorkRecord`, recovery state, or
second lifecycle. It runs no Native solve and creates no application root.

## Exact Interface and owners

`project_execution.py` keeps the existing `ProjectExecution` and
`ExecutedProject` meanings unchanged.

`artifacts.py` owns one operation on the existing `RunDirectory`:

```python
class RunDirectory:
    def record_execution(
        self,
        directory: Path,
        execution: ProjectExecution,
    ) -> None: ...
```

`RunDirectory` remains the sole artifact-name and create-once owner.
`periodic_execution.py` knows no sidecar filename.

After `SessionPool.solve` returns, `PeriodicBatchExecution` records the exact
execution before requesting transmission, polarization, or reference-surface
results. A later observation fault propagates unchanged. A persistence fault
also raises directly before observation begins; there is no grouped failure or
diagnostic fallback.

The existing execution mapping remains exact and redacted. An
`execution.json` without a complete observation proves only solve completion.
`find_work` continues to return a `WorkRecord` only when the entire standard
manifest and both Native projects are complete. A later successful
`record_work` accepts an existing byte-identical execution mapping
idempotently.

## TDD seam

Write fault-injection tests through `PeriodicBatchExecution` and
`RunDirectory`:

1. solve failure writes no execution mapping;
2. completed solve writes the exact existing `ProjectExecution` before the
   first observation call;
3. completed solve followed by response-result or reference-surface failure
   leaves that execution mapping and no `WorkRecord`;
4. the original observation fault type and cause cross the Adapter seam
   unchanged;
5. execution persistence failure prevents observation and raises directly;
6. successful observation reuses the byte-identical execution mapping and
   creates one complete `WorkRecord`;
7. `find_work` ignores an incomplete execution-only directory;
8. recovery, receipts, closure counts, and `PeriodicResponse` Interface remain
   unchanged;
9. Lumerical package exports, runtime DAG, and science dependency ratchets
   remain unchanged.

## Acceptance

- A failed observation can be inspected alongside a durable existing
  `ProjectExecution` without opening `.fsp` or parsing a raw log.
- Complete `WorkRecord` and Authority receipt meanings are unchanged.
- No new persisted schema or exception taxonomy exists.
- Cleanup and activity closure remain owned by existing execution Modules.
- Focused, complete non-live, Pyright, CSU, architecture, and frozen Rust
  checks pass.

## Stop and report

Stop if the change would:

- add an observation-failure record or sidecar;
- classify exception type or text for persistence or control flow;
- admit a receipt or evidence for a failed observation;
- make recovery resume from an execution-only directory;
- introduce an attempt state machine or retry policy;
- alter `ProjectExecution`, `WorkRecord`, closure-count, or
  `PeriodicResponse` meaning;
- require Native execution, Rust changes, or a new public export.

## Do not add

- `ObservationFailureRecord` or any observation-failure schema;
- a second `WorkRecord`, receipt, permit, recovery, or lifecycle abstraction;
- a generic logging framework or solver-error hierarchy;
- traceback, secrets, absolute paths, raw arrays, or raw logs;
- filename literals outside `RunDirectory`;
- a production diagnostic Interface visible to science or callers.
