# CSU 设计原理

CSU 将科研源码中可观察的约定义务转为能够定位和复查的证据。
[编码规范](coding_standards.md) 定义要求；本文解释架构选择及其代价。
具体数据结构、算法和版本身份见[技术参考](technical.md)。

## 用可证明的事实限制判断

源码能证明声明的拼写、语法位置和直接文档关系，却不能独自证明项目的业务词义、单位约定或公开归属。
CSU 将这些信息分开，让每一种结论都能追到对应的责任来源。

| 信息 | 负责什么 | 如何约束影响 |
|---|---|---|
| 固定规则 Standard Law | 规定检查、等级、语言要求和完成条件 | 由产品维护，项目输入不能修改 |
| 源码事实 Source Facts | 证明本次读到的声明和结构 | 使用原始字节、路径及原生语法结构 |
| 项目事实 Project Facts | 补足源码无法证明的项目知识 | 只接受有类型、影响范围固定的登记 |

例如，词表能回答一个未知词元是否属于项目，却不能让候选短名或错误单位后缀通过。
这种限制让项目适配保持可解释，也留下一个明确代价：缺少事实时，结果必须保留不完整。
CSU 校验事实的格式和影响范围；业务事实是否真实仍由项目负责人负责。

## 一个小接口承担完整生命周期

调用者先编译 Authority，再提供源码范围，最终取得一个审查终态。
语言解析、事实索引、规则执行和封存都由审查器内部负责，调用者无需按语言拼装流程。

```mermaid
flowchart LR
    A[编译 Authority] --> B[确定范围并读取源码]
    B --> C[观察物理行与语法结构]
    C --> D[按固定规则判断]
    D --> E[完成各类记录并封存]
    E --> F[文本或 JSON 展示]
```

每次审查独立工作。已编译事实可以被调用者再次使用，前一次的源码结果不成为下一次的依据。
不维护跨次扫描缓存，因此没有缓存失效、迁移和依赖追踪协议；代价是新审查重新读取其范围。
当前负载通过单次读取、有限结构解析和紧凑结果控制成本，实际性能由绑定候选的测量验证。

## 原生结构与直接字节各做合适的工作

逐行扫描不能可靠证明作用域或文档附着，语法树也不必承担物理行与已定位文本的全部检查。
两种观察共用捕获字节：结构解析证明关系，直接检查取得物理事实。
语法损坏阻断依赖结构的判断，独立事实和其他文件仍可检查。

四语言共享规则意图，并保留自己的声明、文档和依赖语法。
语言适配证明名称的角色及文档主体，再交给共同判断；不靠四份独立规则表维持一致性。
命名主体和文档主体也不能混为一谈：函数指针对象有自选名称，函数声明另有 callable 文档义务。

Rust 导入列表以直接语法树表达路径、别名和嵌套关系，由依赖观察负责取得事实，依赖判断负责比较。
两者沿用内部 Interface；普通列表不再因花括号本身受阻，未知语法仍明确记录。
这一扩展不替代 Python 的导入分类或 C/C++ 的构建事实，也不把可解析误当作可安全重排。

`review.rs` 按调用者的阅读顺序组织：审查入口与输入生命周期、结构观察、声明与文档事实、依赖事实、
完成判断与各类规则、最终封存。语言专用辅助紧随其事实归属；共同分组与证据构造集中处理，比较含义保持语言专属。

## 不完整是一种必须保留的结果

“没有发现问题”可能表示源码合规，也可能表示必要事实尚未取得。
CSU 为每个文件固定保留六类完成记录，让这两种情况在结果中可区分。
每类要么完成并记录观察数量，要么受阻并说明原因；完成且数量为零表示确认没有该类对象。

记录数量随文件数和固定类别增长，问题与受阻原因按实际数量保存。
相比为每个对象、义务和条件创建独立收据，这种表示更小，也减少了组合状态。
代价是完成性按类别表达：当前不建立语法损坏区间与全部下游义务之间的传播图。

某类受阻不会抹去已经证明的违规。最终是否通过同时取决于完整性和问题数量。
具体终态和字段含义由[技术参考](technical.md#结果与身份)说明，使用者的处理步骤见[使用说明](usage.md#读取结果)。

## 规则与展示各自保持一个来源

每条固定规则的身份、等级、说明和语义修订与实际判断一起维护。
语言记录提供文档形式、标题顺序及返回要求；这些记录参与执行，不能成为只用来计算摘要的影子配置。
项目输入也不提供脚本、回调、规则开关或可配置等级。

审查先确定并封存语义结果，再展示为文本或 JSON。
这样，改变展示顺序或输出格式不需要重读源码，也不会改变已封存的结论。
身份绑定规则、项目事实、源码与明确范围，使不同条件下的结果能够被区分；它不认证不可观察的业务事实。

## 用公共入口检验架构

行为测试从公共入口核对发现、完整性和 Seal。输入变体放在局部表中，独立语言结构保留独立样例。
辅助只装配输入；具体事实、源码变异和预期留在测试位置。

CSU 自检验证产品和测试源码自身的规范完整性。
冻结的真实源码则检验吞吐、确定性和能力边界，其中已有问题必须保留。
二者提供不同证据；性能好、测试通过或自身合规，都不能代替某个声明分支所需的行为证明。

## 扩展与重新论证

新增规则先回答：检查哪类对象、由什么结构证明、需要哪些项目事实、事实缺失时保留什么结果、事实充分时给出什么等级。
这些答案应贯穿规范、观察、判断、完成记录和公共入口测试。
新增项目词元通常只需维护已有事实；新增事实能力则需要重新审查输入和影响协议。

引入动态规则、跨次缓存、重复完整解析、跨语言语义猜测或更细的传播图，以及突破规模与性能预算时，应重新论证设计。

规模和性能预算统一记录在源码仓库的
[benchmark manifest](https://github.com/HIT-SudoMaker/code-style-unifier/blob/main/docs/fixtures/core/benchmark-manifest.json)。
上限约束复杂度，不是允许填充代码的额度；样例和第三方语料不能承载生产逻辑。
当两个独立的真实实现需要在同一位置替换行为时，再考虑提取接口；只转发数据的辅助层应并回负责约束的位置。
