# CSU 四语言编程规范

> 适用 Python、Rust、C、C++，供代码作者与 AI 共同遵循

本文定义四种语言的源码要求和项目事实允许影响的范围。实现、测试、报告与项目 Authority 必须遵循这些要求。

按检查对象阅读：§2 源码与注释、§3 命名、§4 文档、§5 依赖；§6 提供四语言示例，§7 用于作者核验。
安装和运行见[使用说明](usage.md)，架构取舍见[设计原理](design.md)，数据与算法见[技术参考](technical.md)。

## 1. 规则依据与适用范围

### 1.1 规则依据

1. 用户对当前任务的明确要求
2. 项目需求与公开接口合同
3. 本规范
4. 经本规范约束并通过格式校验的项目 Authority
5. 当前实现与工具默认行为

固定规则涵盖等级、语言要求、优先级和审查终态。源码事实来自规范化路径、已读取字节和原生语法树；
项目事实通过 Authority 补充源码无法证明的信息，只允许以下六类用途。输入格式见[技术参考](technical.md#authority-数据)。

| 项目事实 | 允许影响的范围 |
|---|---|
| `public_callables` | 确定 C/C++ 公开函数的归属并启用公开文档要求；不能降低源码已证明的公开级别 |
| `token_vocabulary` | 确认精确匹配的未知词元；不改变候选名称、保留名称、命名形式或后缀判断 |
| `quantity_concepts` | 登记量值名称与后缀的精确关系；不推断量纲、换算或个例含义 |
| `header_languages` | 为指定的歧义 `.h` 文件选择 C 或 C++；不改变固定扩展名对应的语言 |
| `external_fixed_identifiers` | 按精确的 Rust 函数归属与拼写确认未知名称；其他命名规则照常执行 |
| `dependency_authority` | 补充依赖来源、分类和固定排序规则是否适用；不能自定义顺序、等级或单文件豁免 |

Authority 由项目负责人确认，不是规则配置、豁免名单或真实性证明。CSU 校验输入格式、源码对应关系和允许影响的范围，
不替负责人证明业务事实；信息不足时必须拒绝、标记受阻或要求确认，不得猜成通过。

### 1.2 规范词与终态

| 表述 | 含义与检查方式 |
|---|---|
| 必须 / 禁止 | 在 CSU 可检查的规则中，事实充分且违反要求时报告硬违规 |
| 需确认 | 结构事实成立，但含义需要项目负责人判断，报告待确认问题 |
| 检查受阻 | 缺少必要事实，对应类别不完整；受阻不是一条违规 |
| 建议 | CSU 不设门禁；偏离时由作者承担理由 |
| 作者要求 | 由人工或 AI 单独核验，不新增 CSU 规则、等级或终态 |

报告问题分为硬违规 `HardViolation` 和待确认 `ReviewRequired`；建议不进入执行终态。问题等级、检查完整性
与调用方验收条件相互独立。三零表示硬违规、待确认问题、受阻类别均为零；只有 `Sealed + Complete` 且三零才是
`Clean`。`Incomplete`、`Rejected` 与 `Failed` 都没有通过结论。

### 1.3 当前边界

CSU 检查可解析性、行末注释、作者自选名称、直接附属的源码文档和直接依赖声明。
它不代替编译、运行、格式化、未使用项分析或构建图，也不展开宏、预处理或赋值及跨文件别名；不通过字符串猜测补齐这些能力。
路径与语言接纳、固定解析器身份和完成记录见[技术参考](technical.md)。隐藏清单不能选择源码、指定语言或影响语义身份。

## 2. 源码结构与注释

### 2.1 可解析性

CSU 不执行、导入、编译或链接目标代码。受检源码必须是有效 UTF-8，且固定语言解析器不得产生 `ERROR` 或 `MISSING` 节点；违反时产生
硬违规 `source.parseability`。解析器身份见[技术参考：语言观察](technical.md#语言观察)。

语法损坏会使结构相关类别受阻；物理行等独立事实仍保留，其他文件继续检查。CSU 不在错误树上从关键字、缩进、括号或邻近注释猜测结构。

### 2.2 普通注释与行末指令

普通注释禁止与非注释语法词元位于同一物理行，违反时产生硬违规 `source.trailing_comment`。字符串中的注释字符、独立注释和同一行连续的纯注释
不属于该违规；普通注释不能替代 Python docstring、Rust rustdoc 或 C/C++ 规范文档块。

允许的行末指令必须占满注释正文、位于代码之后、后方没有语法词元，并精确符合下表：

| 语言 | 允许的行末指令 |
|---|---|
| Python | `pragma: no cover`；`fmt: skip`；`type: ignore[...]`；`pyright: ignore[...]`；`noqa: ...` |
| Rust | 不允许行末指令 |
| C / C++ | `IWYU pragma: keep`；`NOLINT(...)` |

省略参数的 `type: ignore`、`pyright: ignore`、`noqa` 和 `NOLINT` 也精确允许。写出代码列表时必须非空，以逗号分隔，且每项只含
ASCII 字母、数字、下划线、连字符或点。空参数、附加正文、近似头、混合指令或跨语言形式仍按普通行末注释判断；项目事实不能扩充这份名单。

### 2.3 注释与叙述风格

本节是作者要求，由人工或 AI 审查。CSU 不用词表、自然语言处理或正则猜测文风，`Clean` 不证明本节已经满足。

- 简短而有用：只写当前代码不能直接表达的目的、理由、约束、不变量或证据
- 直述职责：默认采用“动作＋对象”，必要时补充“方法/条件＋动作＋对象”；不用黑话，类型和字段可用名词短语
- 一行一事：每行只表达一个要点；必要时围绕同一要点换行，不为凑一行堆长句或删限制条件
- 不喧宾夺主：不复述语句或函数名，不写“执行某某内部逻辑”、夸赞、战报、历史流水账或装饰性分隔墙
- 贴近使用：普通注释放在相关代码之前；内部文档摘要说明职责，公开文档保留完整接口合同
- 当前且唯一：删除失效说明；长推导和设计取舍写入文档，代码只保留必要结论与稳定引用

| 信息 | 主要位置 |
|---|---|
| 产品能力、使用入口与已验证优势 | README；不堆实现细节或未经证据支持的宣传 |
| 源码规则、架构取舍、算法与协议 | 分别放在编码规范、设计原理、技术参考中；相互引用，不重复维护规则 |
| 实验与性能结论 | 绑定输入和环境的运行记录；说明文档提供复现和解释入口 |
| 调用所需的参数、返回、失败与安全合同 | 原生 docstring/rustdoc/documentation block |
| 修改局部代码前必须知道的原因、安全条件或不变量 | 代码旁的最短必要注释；不得只留远端文档链接 |

## 3. 语义命名与量值后缀

### 3.1 名称模型与判断顺序

变量等自选名称以完整概念名为中心，按顺序包含语言原生形式、可选的语义角色前缀、完整概念名和可选的表示后缀。
前缀说明角色，后缀说明表示方式；语言专用形式不承担业务含义。

检查时先去除 Python 私有名称前导 `_`、Rust 原始标识符与生命周期标记、C 类型别名尾 `_t`、C++ 私有
成员尾 `_` 等语言形式，再判断业务名称。

每个声明最多报告一项命名问题，优先级如下：

1. 事实不足时标记检查受阻
2. 仅排除语法结构证明的语言固定名称、约定名称或丢弃位置
3. 候选词元优先要求确认其完整概念名
4. 已证明的保留名称、命名形式或后缀缺陷报告硬违规
5. 外部协议注册只能确认精确匹配的未知名称；其他词表外词元仍需负责人确认

### 3.2 语义角色前缀

| 前缀 | 含义 |
|---|---|
| `is_` | 当前是否处于某状态 |
| `has_` | 是否拥有对象或事实 |
| `can_` | 是否具有执行能力 |
| `should_` | 策略是否建议执行 |
| `needs_` | 当前是否需要对象或动作 |
| `lower_` / `upper_` | 允许或配置区间端点 |
| `minimum_` / `maximum_` | 集合、计算或观测所得实际极值 |

禁止 `min_`、`max_` 和复合角色前缀，违反时产生硬违规 `identifier.canonical_form`。CSU 只校验已经写出的
前缀，不从类型或名称推断作者应选择哪种角色。

### 3.3 候选名称与词表

任何原始完整单字符词元都是候选名称，转为小写后长度改变也不影响这一判断。以下 24 个完整希腊字母转写同样是候选：

`alpha beta chi delta epsilon eta gamma iota kappa lambda mu nu` 以及 `omega omicron phi pi
psi rho sigma tau theta upsilon xi zeta`。候选名称只触发待确认问题，需负责人确认其完整概念名，
不会自动改名。`token_vocabulary` 登记项目接纳的完整词元。其他词元统一使用 Rust Unicode 小写处理后再查询候选表和普通词表，
注册与源码检查使用同一处理方式。不按子串、字形、音译或数学等价合并；`phi`、`φ`、`ϕ` 分别判断。
词表外词元同样产生待确认问题。

### 3.4 量值名称登记

表示后缀只说明名称采用的表示方式，不证明量纲、换算、值域或运行正确性。具体名称与后缀的关系由项目登记，
项目示例见源码仓库中的 [靶场指南](https://github.com/HIT-SudoMaker/code-style-unifier/blob/main/docs/fixtures/core/README.md#项目事实示例)，不能当作所有项目必须采用的单位词表。
`quantity_concepts` 要求：概念名为非空 ASCII 小写下划线形式，每个概念至少登记一个后缀。
后缀同样采用该形式，但每个小写段末尾可追加数字；原始后缀不得重复或含空白、大写、首尾或重复分隔符；生成的名称只能有一种拆分。

不符合上述条件的 Authority 在读取源码前被拒绝。登记后，裸概念名判为缺少后缀；登记的组合有效；搭配其他已登记
后缀的组合判为后缀错误。缺少后缀与后缀错误均产生硬违规
`identifier.representation_suffix`；表外复合名称按普通词元判断。`m_per_s2` 可登记，`2m` 与 `m2s`
不可登记；使用强类型封装不会自动免除后缀要求。
大写下划线形式使用同一登记关系：`distance_m` 对应 `DISTANCE_M`；裸 `DISTANCE` 和错误的 `DISTANCE_S`
仍违反后缀规则。该对应只处理名称形式，不推断物理单位等价；混合大小写不产生额外登记。角色前缀同样接纳对应大写形式。

### 3.5 四语言声明形式与结构排除

| 声明用途 | Python | Rust | C | C++ |
|---|---|---|---|---|
| 变量、参数、函数与方法 | `lower_snake_case` | `lower_snake_case` | `lower_snake_case` | `lower_snake_case` |
| 私有变量与成员 | `_lower_snake_case` | 普通绑定形式 | 普通对象形式 | 私有非静态成员为 `lower_snake_case_` |
| 类型、类、结构体与枚举 | `PascalCase`；注解式 `TypeAlias` 可用小写下划线形式 | `PascalCase` | 标签用小写下划线形式；类型别名为 `lower_snake_case_t` | `PascalCase` |
| 导入别名 | 小写下划线形式或 `PascalCase` | 小写下划线形式或 `PascalCase` | 不适用 | 不适用 |
| 模块、命名空间与标签 | 模块绑定用小写或大写下划线形式 | 模块、外部别名与标签用小写下划线形式 | 类型标签与语句标签用小写下划线形式 | 命名空间与别名用小写下划线形式 |
| 枚举变体与枚举项 | `UPPER_SNAKE_CASE` | `PascalCase` | `UPPER_SNAKE_CASE` | `UPPER_SNAKE_CASE` |
| 具名常量 | `UPPER_SNAKE_CASE` | `UPPER_SNAKE_CASE` | `UPPER_SNAKE_CASE` | `UPPER_SNAKE_CASE` |
| 宏定义 | 不适用 | `lower_snake_case` | `UPPER_SNAKE_CASE` | `UPPER_SNAKE_CASE` |
| 类型参数 | 完整 `PascalCase` | 完整 `PascalCase` | 不适用 | 完整 `PascalCase` |
| 常量与非类型参数 | 不适用 | 完整 `UPPER_SNAKE_CASE` | 不适用 | 完整 `UPPER_SNAKE_CASE` |
| 自选生命周期名称 | 不适用 | 完整 `'lower_snake_case` | 不适用 | 不适用 |
作者选择的声明名称必须符合相应语言的命名形式，且不得占用语言保留名称；
违反时分别产生硬违规 `identifier.canonical_form` 或 `identifier.reserved`。

固定名称的排除必须由语法位置证明。Python 只在接收者位置排除 `self`/`cls`，只在模块体或类体的相应赋值位置排除
`__all__`/`__slots__`。Rust 只排除接收者 `self`、类型上下文 `Self`、`'_` 与 `'static`。C 没有
接收者豁免；C++ 排除 `this`、构造与析构的固定拼写及运算符词元。其他位置的同名声明照常判断。

Python 类体中的 `__init_subclass__` 和 `__class_getitem__` 按隐式类方法识别首位 `cls`；显式
`staticmethod`/`classmethod` 装饰器仅在来源已证明时决定接收者角色；同名先前绑定不能当作内建装饰器。
参数列表中的注释不占参数位置，也不代替参数事实。
四语言普通参数注释以及 C++ 模板参数注释均不改变绑定和文档完整性；匿名参数、无法稳定命名的模式仍保留相应缺口。

C/C++ 按各 declarator 的限定层级识别常量：`const int *value` 是可变指针，`int *const VALUE` 是常量指针。
函数指针对象不作为函数声明要求 callable 文档；C++ 范围 `for` 及结构化绑定中的自选名称照常计数和判断。
C++ 按值 `const` 结构化绑定仅在直接结构证明数组元素为常量时按常量检查；无法证明的绑定归属受阻。
引用绑定不因被引对象的 `const` 改判为具名常量；当前数组证明的精确范围见[技术参考](technical.md#语言观察)。

Python 原生库声明由模块或类体内可追溯的直接导入证明，允许直接导入的 `as` 名称；先前的同名绑定、条件导入和精确属性改写
不能当作原生来源。直接继承 `enum.Enum`、`IntEnum`、`StrEnum`、`Flag`、`IntFlag` 的类中，普通字面量和
`enum.auto(...)`/`enum.member(...)` 赋值及最外层直接 `@enum.member` 按枚举常量检查；`enum.nonmember(...)`
赋值按普通值检查。候选词、词表及量值后缀规则仍然适用，未知的最外层枚举方法装饰器不能证明成员角色。
动态值的描述器身份或 `_ignore_` 对成员集合的影响不能直接确定时，标识符类别受阻，不猜测成员角色。
枚举装饰器中的 `staticmethod`、`classmethod`、`property` 同样要求未遮蔽的内建来源或直接导入身份；赋值别名不能补足该证明。
该原生枚举类中的 `_ignore_`/`_order_`，以及直接继承 `ctypes.Structure`/`ctypes.Union` 的类体中的
`_fields_`，属于对应协议的固定赋值名称；普通类的同名绑定不获得排除。

直接调用 `typing.TypeVar`、`typing.ParamSpec`、`typing.TypeVarTuple` 工厂并赋给单个名称时，按类型参数检查，
私有名称仍先去除前导 `_`，不将声明改判为 `TypeAlias`。`typing.TypeAlias` 注解同样要求直接导入来源，允许 `as` 名称。
这些原生库识别不执行源码，不展开函数局部、赋值别名、
跨文件继承或任意工厂的运行时结果，也不通过 Authority 扩大固定名称范围。

`_` 仅在 Rust `let _`、模式通配与 Python `case _` 等语法丢弃位置排除。外部协议固定名称只接纳精确的
Rust 函数身份。`spelling` 必须是源码可观察的 Rust 标识符：普通形式不能是关键字，原始标识符形式另禁
`r#_`/`r#crate`/`r#self`/`r#Self`/`r#super`。`owner` 只接纳 Rust 路径，或带恰好一个生命周期参数的
路径；普通路径段不能是关键字，原始标识符段遵循同一规则，`crate/self/super/Self` 只能是有后继段的首段。
拒绝通配、模式前缀、生成策略、空白和无效的 `fmt::type`；可观察的 `fmt::r#type` 可以登记。C/C++ 字面属性不建立豁免。

## 4. 文档与返回说明

### 4.1 不同对象的文档要求

| 对象 | CSU 检查要求 | 作者指导 |
|---|---|---|
| 公开函数或方法 | 原生文档、摘要，以及按语言排序的参数、返回和失败说明；按声明结构增加必要部分 | 叙述只补充结构化字段无法表达的信息 |
| 内部、私有或嵌套函数与方法 | 原生文档与摘要 | 不必添加空的公开接口章节 |
| 普通注释 | 不能替代原生文档；除允许的行末指令外独占物理行 | 按 §2.3 保留最短必要说明 |
| 文档与注释的表达 | 摘要和规定字段检查可判定的短语、标点与布局要求 | §2.3 的表达要求另行核验，不冒充机器检查结果 |
结构已证明需要文档的声明，必须使用该语言支持且归属明确的原生文档形式。
缺失文档或以普通注释代替时产生硬违规 `documentation.carrier`。摘要必须非空，
且至少含两个连续的中日韩统一表意文字，否则产生硬违规
`documentation.summary`。

内部函数只要求原生文档与摘要，不要求空的参数、返回或失败章节。公开函数
在签名信息完整时必须具有这三个基本部分；没有参数、返回或声明失败时，也必须写该语言规定的空值，不能省略。

摘要与规定字段描述禁止以 `。` 或 `.` 结束，违反时产生硬违规
`documentation.punctuation`。叙述段、代码、URL、路径、版本号和小数不执行全局句号检查。

### 4.2 正文与结构化字段

```text
摘要
一个必需的空行
可选叙述段
按语言要求排序的标题与正文
```

公开文档的叙述区只能位于摘要后的唯一空行与首个规定标题之间。标题重复、失序、缺失或无法归属，以及最后一个
部分之后另加叙述区，均产生硬违规 `documentation.public_contract`。

结构化字段依次由文档标记、字段名称、分隔符、ASCII 空格和描述组成。

同一文档部分的字段名称，必须相对文档标记保持相同缩进；分隔符紧贴名称；分隔符后至少有一个
ASCII 空格，禁止 Tab。描述按字段宽度对齐到最短列，计算使用 `max(width(Identity)) + 1`，最长名称的分隔符
后恰好一个空格；宽度按 Unicode 标量计数。违反任一条件都产生硬违规 `documentation.public_contract`。

结构化与对齐只作用于下表列出的部分，不作用于空值、Rust `- 不返回`、摘要、叙述区或代码行。Rust/C/C++ 的其他正文部分
使用 `- 描述`，不按结构化字段处理。

### 4.3 四语言文档形式

| 语言 | 文档形式与摘要位置 | 公开文档标题顺序 | 需对齐的部分与空值 |
|---|---|---|---|
| Python | 语句块首条 `"""` 字符串；摘要在开引号的下一物理行 | `Args:` → `Returns:` → `Raises:` | 参数、返回、失败；空值为 `无` |
| Rust | 附属的外层 `///`、`/** */` 或字面量 `#[doc = "..."]`；摘要为首个非空行 | `# Arguments` → `# Returns` → `# Errors` → 可选 `# Panics` → 按需 `# Safety` | 参数；空值为 `- 无` |
| C | 紧邻所属声明的 `/** ... */`；摘要为首个非空行 | `参数：` → `返回：` → `错误：` | 参数；空值为 `- 无` |
| C++ | 紧邻所属声明的 `/** ... */`；摘要为首个非空行 | 按需 `模板参数：` → `参数：` → `返回：` → `错误：` → 按需 `效果：` | 模板参数、参数；空值为 `- 无` |

Python 中，非嵌套且名称不以 `_` 开头的函数与协议方法按公开要求检查；类、私有函数、嵌套与局部
函数按内部要求检查。docstring 开闭引号各自独占物理行，开引号后紧接摘要；模块 docstring 产生
`documentation.carrier` 硬违规。`self`/`cls` 不进入参数说明；属性访问器仅在归属有直接证据时共享文档。

Rust 自由函数、固有方法、trait 方法和外部函数均受检。非嵌套且具有无限制 `pub` 可见性的函数，以及公开 trait 的成员，
按公开要求检查；`pub(...)` 与嵌套函数按内部要求检查。
无限制 `pub` 声明与字段、公开枚举变体、不安全 trait 和导出宏也必须有原生文档与摘要。
内层 rustdoc 与普通注释不能替代上述文档。`unsafe fn`/`unsafe trait` 必须有非空 `# Safety`；
安全函数禁止该部分。`# Panics` 可选，但不能代替三个基本部分。

C 区分 Authority 登记的公开函数与结构证明的内部、静态函数，不引入方法模型。C/C++ 的
结构体、联合体、枚举、类、枚举项、宏和非函数字段只要求原生文档与摘要。
歧义 `.h` 的语言只由 `header_languages` 决定；C/C++ 公开级别与唯一归属只由 `public_callables` 补足。
目录、链接属性、`public:` 或 `export` 不能代替该事实；归属不唯一时文档检查受阻。
C++ 模板、构造、析构和运算符根据声明结构增加相应的文档部分。
C/C++ 同一声明中的每个函数 declarator 独立承担文档义务，共享紧邻声明的文档块；相邻对象或声明顺序不能消除义务。

### 4.4 根据声明判断返回要求

返回说明只依据直接声明，分为 `NoValue | Never | Value | Unknown` 四种状态，分别表示无返回值、不返回、有返回值和未知；不返回优先。CSU 不解析别名、导入或类型语义。

| 语言 | 无返回值 | 不返回 | 未知 |
|---|---|---|---|
| Python | `-> None` | `Never`、`NoReturn` 及 `typing.` 形式 | 缺失或不完整注解 |
| Rust | 省略返回箭头或 `-> ()` | `-> !` | 宏或元变量形式 |
| C | 直接 `void` | `_Noreturn` 或无参数、无命名空间的 `[[noreturn]]` | 宏或不完整声明 |
| C++ | 构造、析构、直接或后置 `void` | 无参数、无命名空间的 `[[noreturn]]` | 未推导的 `auto`/`decltype(auto)`、宏或不完整声明 |

无返回值必须写相应语言的空值；有返回值必须写非空的规定内容；Rust 不返回函数必须精确写 `- 不返回`。Python/C/C++ 的不返回状态
没有对应文档标记，因此产生硬违规 `documentation.public_contract`。未知状态使文档检查受阻，不猜成有返回值；
别名仍按直接声明判为有返回值或未知，不追踪其定义。

## 5. 依赖声明

依赖由原生语法树定位；四种语言各用自己的导入语法，不按行长度排序。

| 语言 | 检查对象 | 要求 |
|---|---|---|
| Python | 模块级 `import`/`from` 与精确的 `TYPE_CHECKING` 块 | 禁止 `import *`；按标准库→第三方→项目分类，类内按完整名称字典序排列；同类无空行，跨类一个空行 |
| Rust | 局部连续分组中的 `use` 声明及每层导入列表 | 禁止通配；逐路径段按 `self`→`super`→`crate`→其他名称及含数字段的自然顺序比较；组内无空行 |
| C | 直接 `#include` | 保持源码顺序；缺少构建目标或预处理事实时检查受阻 |
| C++ | `#include`、具名模块或头文件单元的 `import` | 模块导入必须位于顶层、在全局和私有模块片段之外、先于普通声明；缺少目标或模块事实时检查受阻 |

Python/Rust 只有在项目事实标明可安全重排时才检查 `dependency.order`。Python
多模块导入语句、未知分类、非模块作用域或非精确的 `TYPE_CHECKING` 条件会使
依赖检查受阻；Rust 直接导入树含未支持的语法节点时受阻，并保留其位置。两种语言的通配导入均产生硬违规
`dependency.wildcard`。

Rust 支持单层与嵌套列表、别名、`self`/`super`/`crate`、绝对路径和原始标识符。
列表各层与声明之间共用结构比较：先比较路径段，同路径下普通绑定先于通配、通配先于列表；
普通路径延伸先于同前缀的通配或列表。路径和形态相同时，比较别名或递归比较列表项，较短列表在前。
数字段按数值长度和值比较，数值相同再以原拼写打破平局；大小写保留，按字符序比较。
原始标识符的 `r#`、注释、空白和尾逗号不参与排序。绝对路径的起始 `::` 保留为外部路径的空起始段。
空列表和单项列表可以检查，不要求拆分、合并或正规化；完成数量仍按 `use` 声明计数。
未知树不参与相邻声明比较，已识别列表及其他可比较的相邻声明仍独立检查；文件完成性保持受阻。
`rust_reorder_safe` 为 false 时不报告列表或声明排序问题，通配和未知结构仍独立记录。

Python `from .`/`from ..module` 等相对导入由语法证明来源属于当前包，归入项目依赖；绝对导入仍由 Authority 分类。
相对路径按源码中的完整拼写参与同类排序，不据此证明包布局存在、运行时可导入或重排安全。

C/C++ 不把 `*` 解释为通配导入；缺少项目事实的头文件包含、头文件单元或具名模块导入仍使检查受阻。
C++ 模块位置违规独立保留。路径、目录、括号形式或名称出现次数不能用于推断构建目标、分类或是否使用。

## 7. 作者核验

### 7.1 修复核验

可靠修复保留受检声明，以同一 Authority 和范围审查修改后的源码；完整流程见 [修复指引](../.agents/skills/csu-review/references/remediation.md)。
用普通注释替换原生文档、隐藏声明、扩大忽略范围、自动扩词表、降低等级或修改测试预期，都不能证明原问题已经修复。
外部协议固定名称等项目事实，只由项目负责人确认并写入 Authority。

### 7.2 提交前检查

- [ ] 文件可解析；普通注释独占行；允许的行末指令精确命中闭集
- [ ] 名称形式、前缀、候选、完整概念名与后缀的判断正确
- [ ] 受检声明使用原生文档；内部方法有摘要，公开方法有三个基本部分
- [ ] 正文布局、ASCII 空格、最短对齐、标点与声明返回状态相互一致
- [ ] 按 §2.3 人工核验注释简短、一行一事、无复述，并确认技术说明分层放置
- [ ] 按各语言判断依赖；歧义头文件、C/C++ 公开归属及依赖事实已由项目明示
- [ ] 所有类别检查完整；修复后以同一 Authority 重跑并产生新的封存摘要

### 7.3 规则变更

新增词元、量值后缀关系或公开归属只改变项目事实。改变前缀、候选范围、语言规则、
问题等级、判断条件、受检对象或事实能力，属于固定规则变更，须先修改本规范与
[设计原理](design.md)，再补齐通过公共接口验证行为的测试。
